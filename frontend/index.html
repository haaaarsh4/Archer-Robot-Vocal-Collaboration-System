System Pipeline

From microphone to harmony, in under 100ms

Every frame of audio moves through this chain before the robot makes a sound. The pipeline runs continuously at 44100 Hz, chewing through 1024-sample blocks roughly every 23 milliseconds. What follows is a full walkthrough of what actually happens, in order, from the moment sound enters the microphone to the moment the robot's voice comes out the other side.

1
core/audio_capture.py

Audio capture

Everything starts here. The input device is selected through the web UI on the Live Demo tab and sent to the server via a POST request to /pipeline/start, which writes the chosen device index into the config before handing it to AudioCapture. PyAudio then opens a float32 input stream on that device. The stream runs in a background thread and fires a callback every 1024 samples, which at 44100 Hz works out to about 23 milliseconds of audio per frame. Each callback drops those samples into a thread-safe queue. The main pipeline loop sits on the other end of that queue, pulling frames as fast as they arrive without ever touching the audio thread directly. This separation matters: if the pipeline slows down momentarily, the audio thread keeps running uninterrupted, so you never get dropouts or buffer underruns.

PyAudio 44100 Hz 1024 samples / frame float32 threaded callback POST /pipeline/start
2
core/preprocessor.py

Silence detection and normalization

Before any analysis happens, the system needs to know whether a given frame contains real audio or just room noise. It measures the frame's loudness in dBFS using aubio.db_spl(), which returns the sound pressure level as a negative decibel value relative to digital full scale. Frames that come in below the threshold (set to -40 dBFS by default) get discarded immediately. Frames that pass are then normalized to a fixed RMS target, so the pitch detector always receives audio at a consistent level regardless of how far the singer is from the microphone. Without this step, a singer stepping back half a meter would cause the confidence scores to drop and pitch detection to become unreliable.

aubio.db_spl -40 dBFS threshold RMS normalization
3
analysis/pitch_detector.py

Pitch detection

This is where the system figures out what note is being sung. There are now two ways it can do that, and you can switch between them live. The default is still fast and cheap: the 1024-sample frame is split into two 512-sample hops, and each hop is fed through aubio.pitch("yin"). YIN is a time-domain autocorrelation algorithm built specifically for monophonic pitch detection. Unlike FFT-based approaches, YIN looks at the periodicity of the waveform directly rather than its frequency components, which makes it far more robust against harmonics and overtones. A singing voice produces a rich harmonic series, and a naive FFT detector will often latch onto one of those overtones instead of the fundamental frequency. YIN avoids this by construction. Each hop returns a frequency and a confidence score, and only results between 65 and 1200 Hz with confidence above 0.3 are kept.

The second option is RMVPE, a small neural network (a convolutional "DeepUnet" feeding a bidirectional GRU) that predicts pitch directly from a mel spectrogram. It is noticeably more accurate on breathy or quiet singing where YIN tends to struggle, but it is also far more expensive to run. On a CPU it can take longer than a single audio frame's real-time budget, so rather than running it on every hop, the system feeds it a rolling one-second window and only runs a fresh prediction every few hops, reusing the last result in between. This trade keeps the pipeline in real time at the cost of RMVPE's readings updating slightly less often than YIN's. Whichever method is active, the result still passes through the same jump-aware smoother: small drifts are median-smoothed over three frames, but a big jump has to be confirmed by two frames in a row before it is trusted, which stops single bad readings from producing a stray note while still letting real, fast pitch changes through immediately.

aubio YIN RMVPE (DeepUnet + BiGRU) 512 hop size 65 to 1200 Hz range jump-confirm smoothing
3b
analysis/rhythm_analyzer.py

Rhythm and phrase tracking

While pitch detection is running, a parallel process keeps a 2-second rolling buffer of raw audio and uses it to understand the rhythmic structure of what is being sung. Onset detection runs every time approximately one second of new audio has accumulated, using librosa's spectral flux method to find note attacks. Running it on every single frame, as earlier versions of this system did, caused the same onset to be re-detected hundreds of times as the buffer slid forward by just 23 milliseconds per frame. Throttling it to once per second of new audio solves this cleanly.

Beyond individual onsets, the analyzer maintains a phrase state machine with three states: singing, phrase_end, and silence. Any gap of 800 milliseconds or more transitions the state to phrase_end, which signals the harmony engine and synthesizer to wrap up and wait. Tempo is estimated from the distribution of inter-onset intervals and updated every two seconds.

librosa onset detection spectral flux BPM estimation 3-state phrase machine
3c
analysis/phonetic_analysis.py

Phonetic analysis

When enabled, this stage listens not just to the pitch but to the shape of the sound. It extracts 13 Mel-frequency cepstral coefficients and the spectral centroid from each voiced frame. MFCCs capture the resonant character of the vocal tract, which is what makes one vowel sound different from another even at the same pitch. The centroid captures the overall brightness of the sound. Together, these features are mapped to a PhonemeProfile with three values: brightness (0 is dark, 1 is bright), vowel color (0 is a front vowel like "ee", 1 is a back vowel like "oo"), and nasality (0 is oral, 1 is fully nasal).

The goal is not to identify or reproduce Cree language. It is to mirror the physical feeling of what the singer's mouth is doing, so the robot's voice shifts its timbre in sympathy. If a trained sklearn model is available at the path specified in config, it is used for classification. Otherwise the system falls back to the heuristic feature rules.

13 MFCCs spectral centroid Cree vowel mapping optional sklearn model

translation/translate_transformer.py

Turning nêhiyawêwin into English

Once the words are on the page, a translation model turns them into English. There is no existing pretrained model for Plains Cree to build on, so this one is trained from scratch on real nêhiyawêwin text: community-contributed material from the Cree Corpus out of the University of Alberta, plus vocabulary pulled from Watkins' 1865 dictionary of the language. A transformer model reads the Cree and generates the English word by word, checking an exact-match lookup first for phrases it already knows well and falling back to the learned model for everything else.

Cree is a polysynthetic language, meaning a single word can carry what English needs a whole sentence to say, so a fair amount of the engineering here goes into how the text is broken into pieces before the model ever sees it. The full walkthrough, including where the training data comes from and how it's tokenized, lives on the Translation tab.

4c
server.py: score_sentiment()

Reading the emotion in the English translation

Once a phrase is translated, it gets scored on two axes: valence (how negative or positive it is) and arousal (how calm or intense it is). Valence is real, not a stand-in: it comes from VADER, a published, lexicon-based English sentiment tool. Arousal is more honest to call a first pass. There is no free, general-purpose model for "how emotionally intense is this text," so arousal is a hand-built heuristic that combines how much of the sentence VADER scored as emotionally charged at all, intensifier words like "very" or "never," exclamation marks and ALL-CAPS emphasis, and sentence length, since short, punchy lines tend to read as more intense than long ones.

Right now that valence and arousal pair drives the standalone preview on the Sentiment tab, which interval, oscillator shape, and LED color each emotion produces, so a grief-laden phrase and a joyful one clearly sound and look different there. It does not yet feed into the live harmony engine or synthesizer covered below, HarmonyEngine.decide() currently only takes the detected pitch, phrase state, tempo, and Cree phoneme profile. Connecting sentiment into what the robot actually sings, not just the preview, is the natural next step here.

5
synthesis/harmony_engine.py + synthesis/accompaniment_modes.py

Harmony decision

Given a detected pitch, the harmony engine decides what the robot should do with it. It starts by maintaining a rolling history of the last 32 detected pitches, which it uses to infer the current musical key. Key inference runs once per second using the Krumhansl-Kessler algorithm: the distribution of pitch classes in the history is compared against reference major and minor tonal profiles via Pearson correlation, and the root and mode that produce the best fit are selected as the current key.

The actual choice of what to sing now lives in its own file, accompaniment_modes.py, separate from the harmony engine itself. A selector checks a short, fixed list of conditions in order: is the robot's participation switched on at all, is the current phoneme one it should stay silent for, is anyone actually singing right now, is fusion mode forced on, is the tempo above a fast-tempo threshold, and has the current note been sustained long enough to switch to a thickening texture. Whichever condition matches first picks one of ten accompaniment modes, unison shadowing, octave reinforcement, delayed response, timbral thickening, contour following, drone support, call and response, solo humming, and protocol silence, plus triadic harmony as an explicit opt-in for fusion contexts only. The full breakdown of how each function works lives on the Harmony tab.

6a
synthesis/vocable_synthesizer.py

Picking an engine

When the harmony engine issues a sing action, the vocable synthesizer turns that decision into actual audio. There are three interchangeable synthesis engines, picked with one setting in config.yaml (synthesis.engine), and this project's current default is neural_wavetable, not the plain sinusoidal synth this page used to describe as the default. neural_wavetable plays back short vocable takes that were already converted through the trained voice once, offline, ahead of time (see build_vocable_bank.py), then pitch-shifts the right one to match the note being sung right now, cached by the nearest semitone so a repeated note costs nothing after the first time it plays. No live call to the neural model happens here at all, which is exactly what makes this fast enough to keep up with a real singer. This is a different, separate mechanism from the optional live neural reskin covered on the Synthesis tab: that one calls a running model over the network for each note, this one never does.

The other two engines are simpler, and they exist as explicit choices now, not as a silent safety net. wavetable plays back a single recorded take per vowel and pitch-shifts it live. sinusoidal, the original and simplest engine, builds each vowel from four stacked formant resonances, the resonant peaks that give a vowel its recognizable shape, rather than playing back a recording at all. If neural_wavetable or wavetable is selected but its files are missing, the synthesizer now goes silent on that note instead of quietly switching to a different-sounding engine. A wrong-sounding voice showing up unannounced was judged a worse failure than an honest, audible gap.

3 interchangeable engines neural_wavetable (current default) pre-rendered + runtime pitch-shift cache no silent engine fallback

synthesis/vocable_synthesizer.py

Shaping the vowel

Whichever engine renders the note, its vowel color, brightness, and nasality can be shaped by the singer's own detected Cree phonemes: formant targets blend toward the specific phoneme currently active, a high shelf filter brightens the voice when called for, and a notch and peak filter pair shapes nasal sounds. cree_tokenizer.enabled is set to true in config.yaml, with no trained model_path configured, so this runs in heuristic mode: real MFCC and spectral-centroid features pulled straight from the singer's own voice, at a phoneme_influence of 0.6, rather than a flat neutral midpoint. No trained model is required for this to be live.

Separately, a correction that still holds from an earlier version of this page: the sentiment reading described in stage 4c does not feed into this vowel shaping either. It only drives the standalone preview on the Sentiment tab (LED color, interval, oscillator shape), not the formants of the robot's actual sung voice.

formant blend toward active phoneme high-shelf brightness notch/peak nasality active (heuristic mode, phoneme_influence 0.6)

synthesis/vocable_synthesizer.py + synthesis/accompaniment_modes.py

Duet and choir voices

For duet and choir textures, the synthesizer renders several separate voice layers rather than one voice played louder, each with its own small pitch detune, timing offset, and formant scaling, then mixes them together. That is what actually produces the felt sense of several people singing, rather than one voice with reverb added on top. How many voices, how far apart they detune, and how much reverb wash each texture gets are all set per texture in config.yaml (synthesis.texture) and read through TextureParams in accompaniment_modes.py, the same file that now owns mode selection (see stage 5 above). A small algorithmic reverb, built from a handful of comb and allpass filters, is layered onto the mix, with more wash for a choir than a solo voice. A 30 millisecond crossfade is applied between successive notes to remove clicks at note boundaries.

When the neural stage is also on, each of those DSP voice layers ("stems") can be individually re-skinned through the trained voice, one at a time, rather than mixing the ensemble down first and running a single conversion over the mix. That distinction matters: the voice model reads pitch one curve at a time, and several deliberately detuned voices sounding together produce a mistracked, smeared result if they're handed over as one mixed signal. Converting each stem separately means the model always hears exactly one real pitch per call. The lead voice always converts through whichever voice model the person picked; the harmony stems round-robin across every trained voice that's configured, when more than one is available, which is what makes a neural choir sound like more than one person rather than one voice cloned at different pitches. Because the sidecar can only run one conversion at a time, a live take caps how many ensemble voices actually get this treatment (the Neural voices slider next to Voice texture in the demo), while an offline whole-track render can afford to convert every voice in the ensemble.

multi-voice ensemble rendering per-texture config (solo/duet/choir) algorithmic reverb 30ms crossfade synthesis/neural_timbre.py: convert_stems per-voice cap for live takes
6d
output/timing_sync.py

Scheduling and playback

One thing worth being upfront about: this stage only exists in the standalone hardware pipeline, the version of this project that runs directly against a real microphone and speaker (started through pipeline.py). The browser demo on this page plays audio a different way entirely, either a locally generated oscillator in the browser itself, or fetched audio decoded and played through the Web Audio API, so it never touches TimingSync or the code below. Both are real, working parts of the project. They are just two different ways of running it.

In the standalone pipeline, whichever engine renders a note, TimingSync decides exactly when to actually play it. By default it schedules playback 70 milliseconds after the note was detected, which is a deliberate choice, not just processing lag: it gives the robot the feel of a real performer responding with a slight, human delay, rather than an instant, mechanical echo. Once a tempo has been established, that delay gets nudged further to land musically. If less than a quarter of a beat remains at that point, it waits for that beat to land on exactly instead of firing a moment early. If more than three quarters of a beat remains, it waits a full beat longer rather than firing almost right after the previous note. Anywhere in between, it just uses the plain 70 millisecond delay.

If a scheduled note ever ends up waiting more than max_hold_ms (4 seconds by default), it gets dropped instead of played very late, and everything that does play is handed off to the sounddevice library on the configured output device.

standalone pipeline only, not this browser demo 70ms base delay beat-snapping (25% / 75% thresholds) stale-note drop (max_hold_ms) sounddevice playback

Cree Phonetic Layer

The robot doesn't just match pitch. It matches feeling.

When the Cree tokenizer is enabled, the system analyzes the phonetic character of each voiced frame and uses it to shape the robot's voice. The goal is not to reproduce the Cree language but to mirror its resonance and vowel quality.

Cree vowel mapping

How the classifier works

The classifier extracts 13 Mel-frequency cepstral coefficients (MFCCs) and the spectral centroid from each voiced frame. MFCCs capture the shape of the vocal tract, which is what distinguishes one vowel from another. The centroid captures the overall brightness of the sound.

In heuristic mode (no trained model), these features are mapped directly to brightness, vowel color, and nasality values using acoustic rules. The PhonemeProfile that comes out the other side is used by the synthesis engine to adjust the robot's F1 and F2 formant frequencies in real time.

Harmony Engine

Eight ways to sing with a voice, not over it

When Archer sings, the robot picks from eight different musical functions instead of one fixed harmony. It can shadow his exact pitch, echo him a beat later, hold a low note underneath him, follow the shape of his melody, or wait until he pauses and answer him. A regular chord only comes into play when fusion mode is switched on for a contemporary arrangement. Above all of that sits one switch that Archer fully controls, deciding whether the robot sings at all.

Why Not Just Harmonize

A chord is one option, not the assumption

Triadic harmony, singing a third or a fifth above a melody, is the sound most people expect from a harmonizer, because it's how Western pop and choral music are built. But that isn't the only way two voices can relate to each other, and it isn't how Archer's own singing practice works either. A fixed chordal interval is treated as one option among many, reserved for contemporary or fusion moments, rather than the thing the robot defaults to every time it opens its mouth. The rest of the time, it's choosing between functions that come from how people actually accompany each other when they sing together: doubling a voice, echoing it a beat later, holding a drone underneath it, or simply waiting until it stops before answering.

The Eight Musical Functions

What the robot can choose to do

Instead of matching exact notes, the robot tracks the shape of Archer's melody: whether it's rising, falling, or holding level. The exception: triadic harmony
Regular chordal harmony, a third or a fifth above the singer, still exists in the system, but it is reachable only when fusion mode is explicitly switched on for a contemporary or fusion arrangement. It is never the fallback the engine reaches for on its own. This flips the old behaviour of the system, where a fixed interval was always the answer, into something closer to how the eight functions above actually work: chords are a deliberate choice for a specific context, not an assumption baked into every note.
Mode Selection

How the robot decides which one to use

Every audio frame, the engine runs through a short, ordered list of questions to decide which of the eight functions applies. It's deliberately simple and readable right now rather than a learned model, since the priority order itself is still being tuned against Archer's direct feedback. Here's the order it checks, top to bottom, first match wins.

1
core/protocol_guard.py

Is sovereignty switched on at all

Before the engine does anything else, before it even considers what note to sing, it asks one question: is protocol_enabled true? That flag lives inside ProtocolGuard, and it gets checked on every single frame, dozens of times a second. If it's false, the selector returns SILENT immediately. Fusion mode doesn't get evaluated. The tempo threshold doesn't get checked. Nothing else in the priority chain below even runs.

That's deliberate. This check sits first in the function, not because it happened to be convenient to write it that way, but because nothing later in the chain is allowed to override it. Archer can turn the harmony engine off through the on-robot screen or the sound cue, and whichever one he uses flips the same underlying flag. He doesn't need a reason. The engine doesn't ask for one.

2
synthesis/harmony_engine.py

Is this moment protocol-sensitive

Sovereignty being on doesn't mean the robot has blanket permission to sing over anything. Right after the protocol_enabled check, the engine looks at a second, separate condition: is the current phoneme classified as protocol-sensitive? That list, sensitive_phoneme_classes in config.yaml, is empty by default, and that's intentional rather than an oversight. Deciding what counts as sensitive isn't something the engine should guess at on its own.

Instead it's meant to grow the way Archer wants it to, as he reviews his own recordings and identifies specific moments that should stay off limits, and those get added to the list by name. If the current phoneme matches one of them, the engine returns SILENT here too, even with sovereignty otherwise on. Being allowed to participate in general and being welcome in this exact moment are two different checks, and the code treats them that way.

3
synthesis/accompaniment_modes.py

Did Archer just finish a phrase

The engine tracks phrase_state as singing, phrase_end, or silence, and the selector watches for the specific transition from singing to phrase_end. When that transition just happened, meaning Archer was singing a moment ago and has now gone quiet, the selector treats it differently from ordinary silence. It returns CALL_RESPONSE.

That mode reaches back into the pitch history and takes the last note from the phrase that just ended, but it doesn't simply echo it back. If a key has been established, the response resolves toward that key's tonic instead, a blend weighted 65% toward the resolved tonic and 35% toward the exact last note, so the answer feels like it's completing the musical thought rather than just repeating it. Only when no key has been inferred yet does it fall back to a plain echo of the last note. It's the one branch in the whole priority chain built around timing rather than restraint, waiting for exactly the moment Archer stops before it responds, instead of either staying silent through the pause or trying to sing along while he's still going.

4
synthesis/accompaniment_modes.py

Is Archer singing at all right now

If there's no pitch detected, and it isn't the specific moment right after a phrase ends, the selector has to decide what silence means by default. Out of the box, it returns DRONE, a low sustained note pulled from whatever key the engine has inferred, so the space underneath Archer doesn't go completely empty the moment he pauses.

That's a default, not a fixed rule. The silence_when_no_singer flag in config.yaml flips it: set that to true and the selector returns SILENT instead, leaving genuinely empty space until Archer sings again. Which one is right depends entirely on what kind of quiet Archer wants, which is exactly why it's a config value instead of something hardcoded into the logic.

5
config/config.yaml

Has fusion mode been explicitly turned on

Everything else in this priority chain exists specifically so the robot doesn't default to a chord. Triadic harmony still exists in the code, as the TRIADIC mode, but the selector only ever returns it if fusion_mode is set to true in config.yaml.

There's no tempo, no phrase length, no combination of the other conditions above that can trigger it on its own. It's a single boolean, checked explicitly, and it has to be flipped on purpose before the engine will ever reach for a fixed chordal interval.

6
synthesis/accompaniment_modes.py

Is the tempo fast right now

Past a certain tempo, chasing every exact pitch starts working against the music instead of for it. The selector checks tempo_bpm against fast_tempo_threshold_bpm, a value set in config, and if the current tempo clears that threshold, it returns CONTOUR instead of whatever mode would otherwise apply.

Contour following doesn't try to land on Archer's exact notes. It tracks the direction of his melody instead, moving up when he moves up and down when he moves down, over a short rolling window of recent pitches. It's a looser match, but at speed it holds together far better than a robot straining to hit targets that keep moving before it can catch them.

7
synthesis/accompaniment_modes.py

Has Archer been holding one note for a while

The selector keeps a running count, frames_on_current_note, tracking how long Archer has held his current pitch. Once that count passes sustain_frames_for_timbral, a threshold set in config, the selector returns TIMBRAL instead of continuing to match the note plainly.

Timbral thickening keeps the exact same pitch, but instead of one voice it renders two, tuned about 3 cents apart on either side of that pitch (6 cents total spread -- see synthesis.timbral_detune_cents in config.yaml), with a touch of formant variation so the second voice reads as a separate singer rather than a copy-pasted clone of the first. The result is chorus-like richness rather than a flat, static double sitting on top of a note that's already been going on for a while. This mode always renders both voices, regardless of whatever Voice Texture is set to -- Solo elsewhere caps things at one voice, but here the second voice IS the mode, not an extra on top of it. Long sustained notes are where that kind of texture actually gets noticed, so that's exactly where the extra work happens.

config/config.yaml

None of the above

If none of the checks above have returned anything, the selector falls through to default_mode, whatever's configured in config.yaml, unison shadowing out of the box. This isn't a fallback in the sense of something going wrong. It's just the answer for the ordinary middle of a phrase, where nothing about the timing, tempo, or duration is asking for anything specific to happen.

The robot sings Archer's note back to him, exactly. It used to be the only thing the system could do at all. Now it's one branch out of eight, reached only when the other seven have nothing to say, but it's still the one doing most of the actual work, the same way most of a real conversation is quiet agreement rather than anything dramatic.

Sovereignty

The switch that overrides everything else

None of the eight functions above matter if Archer hasn't chosen to have the robot participate. That choice needs to be his, guaranteed, and impossible for any part of the accompaniment logic to talk its way around. The system checks this before any musical decision is made, not after, through the robot's own on-robot screen, with a sound cue as a backup in case the screen isn't within reach.

On-robot screen
A control panel Archer can reach directly
The robot is meant to carry its own screen, where Archer can switch the harmony engine on or off and adjust settings like the default mode or fusion mode in real time, without needing a laptop or a second person in the room. A sound cue, a short burst of low, quick hums, backs up the same switch, so there's always a way to shut the robot down even if the screen isn't within reach in the moment.

Try it below: switch sovereignty off, then pick any of the eight modes and sing into the microphone. The robot stays silent no matter which mode is selected, because the check happens first, before any of that mode's logic ever runs.

Scale Lock

Why the robot never plays a wrong note

Whatever pitch a mode proposes, unison, an octave down, a delayed echo, gets snapped to the nearest note in the key the engine has inferred, before it's ever sung. The key is re-estimated once a second using the Krumhansl-Kessler algorithm: the distribution of Archer's recent pitches is compared against reference major and minor tonal profiles, and the closest match becomes the current key. Even if a mode's raw calculation lands slightly off, the engine nudges it to the nearest valid scale degree, so the result always sounds intentional. Drone support is the one exception, since a grounding root note is meant to sit outside the melodic scale entirely.

Voice Synthesis

One toggle, two different ways to hear the robot sing

DSP and Neural are the two positions of the Robot Voice switch on the Upload and Sing-live panels. This is what those two words actually mean, what's different about the resulting sound, and where in the code that difference happens.

DSP: signal processing on real recorded takes Neural: one extra pass through a trained voice model DSP always runs first, in both modes
synthesis/vocable_synthesizer.py + synthesis/neural_vocable_bank.py + synthesis/neural_timbre.py + neural_env/rvc_server.py
The Two Modes, Plainly

What "DSP" and "Neural" actually mean here

"DSP" stands for Digital Signal Processing, the general name for audio math that isn't a neural network: filtering, resampling, pitch-shifting. "Neural" means a trained neural network actually runs and produces sound. Both modes start from the exact same place, the DSP synthesizer building a note from a real recorded vocable take. Neural just adds one more step on top.

DSP (real-time)

What it is. A pre-recorded "oh", "hey", "yeah" take, pitch-shifted with math (a phase vocoder) to whatever note the harmony engine decided on. No neural network runs during a live performance. It's the same category of technique as time-stretching a sample in any DAW.

Why it's instant. A pitch shift on a clip that's already sitting in memory takes a few milliseconds. Nothing here is slow enough to fall behind a live singer.

synthesis/neural_vocable_bank.pyphase vocoder pitch-shiftPOST /api/dsp/render-track
Neural (offline render)

What it is. The complete DSP output above, built exactly the same way, then sent through a real trained voice-conversion model (RVC-style) for one additional full pass. This is genuine neural network inference, not a filter.

Why it's slower. Running a trained network takes real compute, 50ms to a couple of seconds depending on length and hardware, which is why this mode is "analyze, then play" instead of instant. It's a genuine second step, not a setting inside the DSP synthesizer.

neural_env/rvc_server.pysynthesis/neural_timbre.pyPOST /api/neural/render-track

DSP is always what happens. Neural is DSP, plus one more step. Neural mode never skips the DSP stage, it just doesn't stop there.

DSP Mode, In Detail

How a note actually gets built from a recording

Every vocable, "oh", "cold", "moon", whatever's in the vocable bank, started as a short raw take, then got run through the neural voice model exactly once, offline, by build_vocable_bank.py. That converted clip is saved to synthesis/samples/neural/ and, from that point on, DSP mode never touches the neural model for it again. It only pitch-shifts that saved recording.

neural_vocable_bank.py keeps every loaded take's own natural pitch on file, so when the harmony engine asks for a note, it picks whichever recorded take is closest in pitch to the target and shifts from there rather than always shifting the same one clip by a huge amount. A shift is capped at 14 semitones from that take's own pitch, a bit over an octave, since past that a single recording stops sounding like a consistent voice, it just gets clamped to the closest achievable pitch rather than refused outright, so a note is never simply dropped for being out of range.

Deciding when a new note should even start is its own piece of logic in synthesis/harmony_engine.py. Pitch is compared in cents rather than raw Hz, since a fixed frequency gap means something completely different low in a voice than high in it, and a shift has to hold for two consecutive readings before it counts as a real new note, so ordinary vibrato or a moment of detector noise doesn't retrigger the whole sound mid-note. A brief dropout, a missed frame, a breath, holds the last note steady for a short grace window instead of cutting it off outright.

synthesis/build_vocable_bank.py synthesis/neural_vocable_bank.py synthesis/harmony_engine.py synthesis/vocable_synthesizer.py
Two Voices, Not One

The DSP voice always exists. The neural voice sits on top of it.

The DSP synthesizer is the foundation and it never goes away, whichever engine is active it stays fast and cheap enough to keep up with a live singer with no perceptible lag (see the Architecture tab for how its own engines work). The neural stage covered below sits after that, not instead of it. It takes whatever the DSP synthesizer produced and runs it through a trained voice conversion model, so pitch and timing still come from the DSP layer and the harmony engine, but the actual timbre, the thing that makes a voice sound like a specific person, comes from a real trained model. As currently configured this stage is switched on (synthesis.neural.enabled: true). If it's off, not installed, or its model files are missing, the pipeline just keeps singing in the plain DSP voice, nothing silently degraded.

The Sidecar Process

What actually happens when rvc_server.py starts

Before any conversion can run, something has to load the trained voices into memory and sit ready to receive audio. That's the whole job of rvc_server.py. Starting it reads the same config.yaml the main app uses, resolves every path in synthesis.neural.model_paths and index_paths relative to the project root, and loads the RMVPE pitch model once, shared across every voice, since it's the same network regardless of which trained voice ends up being used. Each trained voice is then loaded one at a time. If a voice's file is missing or its checkpoint doesn't load cleanly, that one voice is marked as failed and the sidecar keeps starting the rest rather than refusing to start at all, so one bad file doesn't take every voice down with it.

Each voice that loads successfully is immediately warmed up with a short burst of silent audio run through the full conversion path once, before the sidecar ever reports itself ready. Without this, the very first real note sung after startup would pay the full one-time cost of everything PyTorch needs to set up internally, a much longer delay than any note after it. Paying that cost once at startup, on fake audio nobody hears, means every real note converts at the sidecar's normal speed from the first one onward. GET /health on the sidecar reports exactly which voices loaded, how long each one's warm-up took, and whether it's running on CPU or GPU.

One thing about the sidecar's design shapes almost everything downstream: it can only run one conversion at a time. A single lock around the actual inference call means a second request that arrives while one is already running either waits its turn or gets told the sidecar is busy, depending on which endpoint is calling it. That single detail is the reason the three usage patterns further down exist as three separate things instead of one.

Neural Mode, In Detail

What actually happens inside that one extra pass

The neural voice model is heavy. Running it in the same process as the real-time pipeline would mean one slow inference call could stall every other connection on the server while it runs. So it lives in its own FastAPI process, the sidecar described above, started separately and talked to over HTTP. The conversion code itself is a direct port of RVC-Project's own official inference logic, built from the same HuBERT, RMVPE, and generator files the official tooling ships, rather than a third-party reimplementation, since loading the exact same trained checkpoint through a different reimplementation of the same architecture doesn't reliably give back the same result.

1
neural_env/infer/hubert.py

Extracting what was actually said

The DSP audio first goes through HuBERT, a speech model that turns raw audio into a sequence of features describing its phonetic content, independent of who's voicing it. This is the part that carries the vocable shapes and their timing forward into the new voice.

HuBERT (fairseq base, RVC v1/v2 layers) shared across all loaded voices
2
neural_env/rvc_pipeline.py: RMVPEPitchExtractor

Extracting the pitch, again, separately

The neural voice model needs its own accurate read on pitch to reconstruct the melody correctly, using the same RMVPE network described on the Architecture tab, run again here since the target voice's pitch has to line up exactly with what the HuBERT features are carrying. One shared instance is created when the sidecar starts and reused for every conversion, with calls serialized behind a lock since RMVPE isn't documented as safe to call from multiple threads at once.

RMVPE one shared instance, not per-voice
3
neural_env/rvc_pipeline.py

Blending in the trained voice's own character

Each trained voice comes with a FAISS index built from that voice's own training data. The extracted content features are partially replaced with their nearest neighbors in that index, controlled by an index rate (0.75 as currently configured), which is what actually pulls the output toward sounding like the specific trained voice rather than a generic conversion. A separate protect setting (0.33 by default) shields unvoiced consonants and breath sounds from being overwritten by this blend, since those carry very little pitch information and are the easiest part of a conversion to damage.

FAISS nearest-neighbor index index_rate 0.75 protect 0.33
4
neural_env/rvc_pipeline.py: RVCOfflineVoice

Generating the final audio

The blended features and the extracted pitch go into the trained voice's own generator network, which produces the final waveform in that voice's timbre and target sample rate. The result is what gets sent back to the main pipeline, resampled and mixed in place of the plain DSP audio.

Most of what this sidecar renders is a single short note rather than a long file, so a bit of audio is mirrored onto both ends of the clip before any of this runs, then trimmed back off the finished result afterward, since without it the very start and end of every note (exactly what a listener notices most) would generate with no context on one side. The checkpoint load itself is checked rather than trusted, too: if any layer name in a trained voice file doesn't line up with the model it's being loaded into, that mismatch is now logged instead of silently leaving part of the generator randomly initialized.

trained generator (.pth) per-voice target sample rate edge padding for short clips checkpoint mismatches now logged
Keeping Drums Out Of The Voice Model

Why "Sing along with instruments: Off" needed its own fix

The trained voice model doesn't know or care what a drum hit is, it just converts whatever's in the frame of audio it's handed. If that frame contains a drum transient, the model reads that as a strange, sudden change in pitch and timbre and dutifully tries to re-sing it, which is what a "singing drum machine" glitch actually is. The fix has to happen before the audio ever reaches the trained voice, not after, and it happens in server.py, not inside the sidecar itself.

1
server.py: _separate_vocal (Demucs)

Separating the voice from the instruments, properly

The first thing tried, and the one that actually solves the problem on a real song, is full source separation using Demucs (the htdemucs model). It splits the uploaded audio into drums, bass, other instruments, and vocals, and only the isolated vocal stem is ever sent to the trained voice. The separated instrumental is thrown away entirely rather than mixed back in afterward, which is exactly what "Sing along with instruments: Off" is meant to mean: the robot performs solo, with no drum or instrument sound anywhere in the output, not a full remix with a converted vocal laid back over the original backing track.

This replaces an earlier approach that tried to find and silence instrumental-only stretches of time in the mixed track. Measured against a real recording from this project, the harmonic and percussive energy stayed intertwined for almost the entire song, meaning the vocal and the drums are sounding at the exact same instant nearly throughout, not taking turns in separate sections. There's no time-range mute that can remove a drum hit without also erasing whatever note is being sung over it at that same moment, so muting by time was never going to be a real fix. Separating the two signals apart first is.

Demucs htdemucsisolated vocal stem only sent to RVCinstrumental discarded, not remixed
2
server.py: _silence_instrumental_spans

A lighter fallback for short clips

Demucs needs a real stretch of audio to separate well, so it's only used on clips of about 6 seconds or longer. Below that, and anywhere Demucs itself fails partway through, a much lighter frame-by-frame check steps in instead: every 100 milliseconds of audio is scored on how harmonic versus percussive it is, and how tonal versus noise-like it is, and any stretch that reads as instrumental gets faded to silence rather than passed through. This won't remove a drum hit landing on top of real singing the way full separation does, but on a short streamed chunk, or a stretch that's genuinely drums with nobody singing, it still keeps that content from ever reaching the trained voice.

Where This Shows Up

Three different ways to reach the neural voice

Because the neural stage is genuinely slow on a CPU, often 50 to 500 milliseconds per call, it can't be dropped into the live microphone path the same way YIN or the DSP synthesizer are. There are three separate backend routes to it, each trading speed for something else, though not all three are currently wired up to a control in the interface.

Live mic and demo pages

Setup And Current Limits

What it takes to run, and what it doesn't do yet

The neural stage needs a trained voice model (a .pth file) and, ideally, its matching FAISS index, both pointed to from synthesis.neural.model_paths and index_paths in config.yaml, plus the RMVPE checkpoint used for pitch extraction. The sidecar is started separately from the main server and needs to be reachable at the URL set in synthesis.neural.sidecar_url before synthesis.neural.enabled does anything. GET /neural/status reports whether it's loaded, enabled, and actually reachable, and the sidecar's own GET /health reports which specific voices loaded successfully.

There's no GPU attached right now, so the sidecar runs on CPU, which is the reason the live path renders one note at a time instead of streaming continuously, and the reason the whole-track modes exist at all. Multiple trained voices can be configured at once, and a voice index picks between them per request.

Step One: Transcription

How your voice becomes text in the first place

Before any translation or sentiment reading can happen, whatever you say into the mic has to become text. That is its own real problem, separate from translation, and it is the very first thing that runs. Three stages, in order.

1
server.py: /ws/live-transcribe, /api/transcribe

Two engines, doing two different jobs

The moment you start talking, a small model called Vosk runs entirely on this server and streams back a rough guess of what it hears within a couple hundred milliseconds, shown in italics while you are still speaking. An earlier version leaned on the browser's own built in speech recognizer for that instant feedback, but that only works in official Chrome or Edge and quietly depends on sending your audio to a private Google service, so it was replaced with Vosk, a real model that needs nothing outside this server.

Once you pause, a second, much slower and far more careful model takes over, a local build of OpenAI's Whisper, and transcribes the whole phrase properly. The rough live guess then gets replaced, phrase by phrase, once that careful version is ready. Every finalized phrase stays clickable afterward, so you can revisit its translation and sentiment reading again without saying it twice.

Vosk, fully local partial results in ~100 to 300ms Whisper for the final pass replaces browser speech recognition
2
server.py: _classify_segments

Catching what it doesn't actually know

Whisper is a language model as much as it is an audio model, and when it hears something that is not really speech, a hand drum, wordless vocables in a chant, it does not say so. It confidently invents a plausible sounding English sentence instead, because it was trained to always produce fluent text. That is a real and well documented failure mode, not a rare glitch, and left unchecked it looks exactly like a genuine transcription.

To catch this, every stretch of audio Whisper transcribes gets checked against three numbers it already calculates about its own output: how confident it is that real speech was even present, how likely its wording is to be a real sentence rather than a guess, and how repetitive or strange the phrasing came out. These are the same three warning signs OpenAI's own Whisper documentation flags as signs of unreliable output. A segment that fails the check gets labeled honestly as unclear instead of being shown as if it were a real transcription.

confidence, not just text, gets checked OpenAI's own reliability signals labeled honestly instead of guessed
3
server.py: _detect_instrument_spans, _detect_percussive_spans

Labeling sound that was never going to be words

A drum hit or a violin line is not mistranscribed speech, it is not speech at all, so asking a speech model to transcribe it is the wrong tool for the job no matter how well that model is checked. Instead, a separate pass listens for a steady, regular rhythmic pulse across the audio, the kind a hand drum or shaker produces, and marks that stretch honestly as instrumental rather than leaving it blank or guessing at words.

Where a real sound classifier is installed, this goes further and names the actual instrument, violin, flute, drum, guitar, and dozens more, using a model trained on over five hundred everyday sound categories. Where it isn't installed, the system falls back to the rhythm only version rather than failing, so the page still works either way, just with a plainer label.

rhythm detection, always on named instruments, when available graceful fallback either way

Step Two: Translation

How the translation layer underneath it gets built

This is the groundwork the sentiment reading depends on. Five stages, in order, from raw source text to a working translator. The sentiment layer itself picks up right after this, further down the page.

1
translation/build_translation_corpus.py + sentence_aligner.py

Gathering and lining up real sentences

The starting point is the Cree Corpus, a collection of nêhiyawêwin texts out of the University of Alberta covering everything from Bible passages to Solomon Ratt's Cree language workbooks to literacy group materials and social media posts. Each text exists as a separate Cree file and English file, and for a lot of them the number of lines on each side doesn't match, sometimes a sentence gets split differently between the two, sometimes it comes down to how the original was formatted.

Lining these up by hand isn't practical at this scale, so a length-based sentence aligner compares how long each line is in Cree against how long the matching stretch is in English and works out the most likely pairing, similar to how sentence alignment has been handled in machine translation for decades. That one piece of engineering took the usable data from about 1,030 sentence pairs up to 8,397, recovering thousands of real sentences from Bible passages and workbooks that would otherwise have been unusable.

length-based alignment recovered 8,397 pairs from 1,030 handles split and merged lines
2
translation/watkins_to_pairs.py + combine_corpora.py

Bringing in a 160 year old dictionary

Modern nêhiyawêwin text online is genuinely rare, so the corpus above gets extended with vocabulary pulled from Watkins' 1865 "A Dictionary of the Cree Language," a public domain historical dictionary that was scanned, OCR'd, and parsed into individual word entries.

Each dictionary entry is a single word in each language rather than a full sentence, so it gets blended in carefully instead of dumped in at full volume. Mixing in too many single-word examples would teach the model that short, choppy answers are normal, so the ratio of dictionary entries to real sentences is capped, which keeps sentence-level fluency as the dominant signal while still closing real vocabulary gaps.

Watkins (1865) dictionary OCR + structured parsing ratio-capped blending public domain source
3
translation/cree_morfessor.py + tokenizer.py

Splitting Cree the way Cree actually splits

nêhiyawêwin is polysynthetic, meaning a single word can carry what English needs a whole phrase to say, built from a root plus a long chain of prefixes and suffixes. Standard subword tokenization, the kind most translation models use, looks for whatever character sequences repeat most often in the raw text, which tends to chop polysynthetic words apart in places that don't line up with any real piece of the word's meaning.

Instead, an unsupervised morphology learner called Morfessor studies the corpus first to find the word parts that actually recur as real prefixes, roots, and suffixes, and standard subword encoding only runs on top of those pieces afterward. Training and translation both apply the exact same segmentation automatically, so the two stages can never quietly drift out of sync with each other.

Morfessor segmentation SentencePiece BPE on top polysynthetic-aware shared Cree / English vocabulary
4
translation/model.py + train_transformer.py

Training the model itself

There is no existing pretrained model for Plains Cree anywhere to build on, unlike English, French, or Spanish, which all have huge pretrained models available off the shelf. The translation model here is a transformer encoder-decoder built and trained from scratch, sized deliberately small rather than huge, so its capacity roughly matches the amount of real training data available. An oversized model on a small dataset just memorizes the training examples instead of learning to generalize.

Training holds out a validation set of real sentence pairs the model never trains on, so progress gets tracked honestly against data it hasn't seen, and training stops automatically once validation performance stops improving rather than running blindly for a fixed number of steps.

transformer encoder-decoder trained from scratch train / validation split early stopping
5
translation/translate_transformer.py

Producing an actual translation

At translation time, the system checks an exact-match lookup table first. A phrase the model has seen word for word during training is more trustworthy coming straight from that lookup than from anything the neural model might generate on its own. Anything new goes to the transformer, which builds the English translation word by word using beam search, keeping several candidate translations alive at each step instead of committing early to a single guess, and returning the highest-scoring complete sentence at the end.

exact-match fast path beam search decoding length-normalized scoring

Pitch and rhythm tell the robot what notes to sing. This layer tells it how to feel about it. With the translation layer above turning the sung nêhiyawêwin into English, this stage reads the emotional tone of that translation, scoring it for valence (how negative or positive) and arousal (how calm or intense). Song Notes Assistant

A chat assistant that only knows what Archer actually wrote down

Tucked into the Archer-Bot bubble in the corner of every page is a small local language model that answers questions about Archer's songs, their meaning, their backstory, how they came together, using nothing but the notes Archer has actually written. No API key, no cloud request, no internet connection needed. The model, the search index, and the optional spoken replies all run right here on this machine.

Retrieval augmented generation Local LLM via Ollama or llama.cpp sentence-transformers embeddings Fully offline Optional spoken replies via Piper
chat/chat_api.py + chat/rag_index.py + chat/llm_client.py + chat/tts_engine.py
Why Retrieval, Not Just A Model

The model is only allowed to answer from the notes it's given

A general purpose language model asked about a song it has never heard of will not usually say it doesn't know. It will guess, and it tends to sound completely confident while doing it. That's a real problem for something meant to speak for Archer's own songs, so this assistant is built to never just answer from whatever the model already happens to know. Every question first goes through a search step over Archer's own written song notes, plain markdown or text files sitting in a song_notes folder, and only the passages that search step actually finds get handed to the model as its answer key.

If nothing relevant turns up in that search, the model is instructed to say plainly that it doesn't have notes on that yet, instead of filling the gap with something that sounds right but isn't. The system prompt spells this out directly: answer questions about song meaning, backstory, and creation using only the context passages given below the question, and if the context doesn't contain the answer, say so instead of guessing.

How One Question Becomes An Answer

What actually happens between typing a question and getting a reply

Every message sent through the Archer-Bot bubble runs through the same handful of steps before a reply comes back.

1
chat/rag_index.py: SongNotesIndex.build_or_load()

Turning song notes into searchable chunks

The first time the app starts, or whenever /api/chat/reindex is called, every markdown or text file in song_notes/ gets read and split into chunks of roughly 900 characters each, cut along paragraph breaks so a chunk doesn't get sliced off mid thought. If a single paragraph runs longer than that on its own, it gets split with a sliding window instead, keeping a 150 character overlap between pieces so an idea spanning the cut point doesn't lose context. Each chunk is then turned into a 384 number vector by a small sentence transformers model, all-MiniLM-L6-v2, running on the CPU. Rebuilding all of that from scratch on every restart would be wasteful, so each file's content is hashed and checked against a saved manifest, and a file only gets re-chunked and re-embedded if its content has actually changed since last time.

all-MiniLM-L6-v2 embeddings ~900 char chunks, 150 char overlap hash based incremental caching
2
chat/rag_index.py: SongNotesIndex.query()

Finding the passages that actually answer the question

When a question comes in, it gets embedded with that same model and compared against every stored chunk using cosine similarity, a measure of how closely two vectors point in the same direction. The four closest chunks are pulled out, but only the ones that clear a minimum similarity score of 0.15 make the cut. A passage that scores below that line is judged too unrelated to help and gets left out entirely, rather than included just to fill out the count.

top_k = 4 min_score 0.15 cosine similarity search
3
chat/llm_client.py: LocalLLMClient.chat()

Assembling the actual prompt

The retrieved passages get joined together under a short header, "Context from your song notes," and appended to the question before anything goes to the model. A fixed system prompt sits above all of that, telling the model to act as a warm guide to Archer's songs, to answer only from the context it's given, and to say it doesn't have notes on something instead of inventing an answer. It also carries one specific redirect: if someone asks for an actual Cree translation rather than just discussion of a Cree phrase, the model is told to say that request is being routed to the app's dedicated Cree translator instead of attempting the translation itself. The last eight turns of the conversation are kept and sent along too, so the assistant can follow a back and forth without losing the thread, though the search step above runs fresh for every single question.

system prompt enforces context-only answers last 8 turns of history kept Cree translation requests redirected
4
chat/llm_client.py: backend dispatch

Where the actual thinking happens

The assembled prompt goes to one of two backends, chosen in config.yaml. The default is Ollama, a local server the app talks to over plain HTTP at 127.0.0.1:11434, running an 8 billion parameter instruction tuned model by default. The alternative is llama.cpp, which loads a GGUF model file directly inside the same process instead of relying on a separate server, useful for a simpler setup with one less thing running in the background. Either way, replies are generated at a fairly low temperature of 0.4, favoring consistent, grounded answers over creative ones, and capped at 500 tokens so replies stay conversational instead of turning into an essay. If Ollama isn't running, or the configured model hasn't been pulled yet, the app fails with a clear message telling you what to run, instead of a raw connection error.

Ollama (default) or llama.cpp backend temperature 0.4 500 token reply cap fully local inference
5
chat/chat_api.py: chat()

Sending the reply back, and sometimes a voice with it

The finished reply comes back together with the list of source file names the search step actually pulled from, so it's clear which notes an answer is grounded in rather than just trusting the polished text on its own. If the message was sent in spoken mode, that reply text also gets passed to a local Piper text to speech engine and comes back as a base64 encoded WAV file the chat bubble plays out loud. If no Piper voice has been configured yet, the reply still comes back as text, along with a plain note that spoken replies aren't set up rather than the request failing outright.

sources returned with every reply optional Piper text to speech graceful fallback to text only
Where This Shows Up

Behind the chat bubble in the corner

All of this lives behind the small Archer-Bot bubble in the bottom right of every page, not a separate page of its own, so it's available no matter which tab you're actually looking at.

"Ask about songs" tab

The main flow described above. Typing a question in the Ask about songs tab sends it to POST /api/chat along with the recent conversation history and a choice of a text or spoken reply. GET /api/chat/health reports back whether the notes index actually built and how many chunks it holds, so a broken setup shows up clearly instead of quietly returning empty answers.

Rebuilding the index

For when the notes themselves change. Song notes aren't meant to be edited constantly, so the index isn't rebuilt on every request. Whenever a note gets added or changed, POST /api/chat/reindex forces a fresh pass over song_notes/, picking up anything new without needing to restart the whole server.

POST /api/chat/reindexhash based, only changed files get re-embedded
Setup And Current Limits

What it needs to run, and what it doesn't do yet

For the search step to find anything, song_notes/ needs actual markdown or text files in it, since an empty folder means every question comes back as "no notes on that yet." For the model itself, Ollama needs to be installed and running locally with the configured model already pulled, set through chat.ollama_model in config.yaml, or chat.backend can be switched to llama_cpp with chat.gguf_path pointing at a downloaded GGUF file instead. Spoken replies need a Piper voice file set at tts.voice_path. None of these are hard requirements for the app to start. Each one just quietly falls back instead, no chunks indexed, a clear error asking you to start Ollama, or text-only replies, rather than crashing.

One honest limitation worth stating plainly: the search step only ever looks through the plain written notes in song_notes/, not the lyrics, transcripts, or anything the harmony and synthesis pipeline generates live while Archer is actually singing. It can talk about a song's backstory in real depth, but it has no idea what just happened musically thirty seconds ago in a live performance, that's a different part of the system entirely. And because the embedding model is small and runs on CPU by design, for speed, a question that means the same thing as a note but shares very little of its actual wording can sometimes score just under the 0.15 threshold and get skipped instead of matched. That's a deliberate trade-off in favor of not guessing, not a bug.
