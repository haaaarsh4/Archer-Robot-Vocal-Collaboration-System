System Pipeline

From microphone to harmony, in under 100ms

Every frame of audio moves through six stages before the robot makes a sound. The pipeline runs continuously at 44100 Hz, chewing through 1024-sample blocks roughly every 23 milliseconds. What follows is a full walkthrough of what actually happens, in order, from the moment sound enters the microphone to the moment the robot's voice comes out the other side.

1
core/audio_capture.py

Audio capture

Everything starts here. The input device is selected through the web UI on the Live Demo tab and sent to the server via a POST request to /pipeline/start, which writes the chosen device index into the config before handing it to AudioCapture. PyAudio then opens a float32 input stream on that device. The stream runs in a background thread and fires a callback every 1024 samples, which at 44100 Hz works out to about 23 milliseconds of audio per frame. Each callback drops those samples into a thread-safe queue. The main pipeline loop sits on the other end of that queue, pulling frames as fast as they arrive without ever touching the audio thread directly. This separation matters: if the pipeline slows down momentarily, the audio thread keeps running uninterrupted, so you never get dropouts or buffer underruns.

PyAudio 44100 Hz 1024 samples / frame float32 threaded callback POST /pipeline/start
2
core/preprocessor.py

Silence detection and normalization

Before any analysis happens, the system needs to know whether a given frame contains real audio or just room noise. It measures the frame's loudness in dBFS using aubio.db_spl(), which returns the sound pressure level as a negative decibel value relative to digital full scale. Frames that come in below the threshold (set to -40 dBFS by default) get discarded immediately. Frames that pass are then normalized to a fixed RMS target, so the pitch detector always receives audio at a consistent level regardless of how far the singer is from the microphone. Without this step, a singer stepping back half a meter would cause the confidence scores to drop and pitch detection to become unreliable.

aubio.db_spl -40 dBFS threshold RMS normalization
3
analysis/pitch_detector.py

Pitch detection

This is where the system figures out what note is being sung. The 1024-sample frame gets split into two 512-sample hops, and each hop is fed through aubio.pitch("yin"). YIN is a time-domain autocorrelation algorithm developed specifically for monophonic pitch detection. Unlike FFT-based approaches, YIN looks at the periodicity of the waveform directly rather than its frequency components, which makes it far more robust against harmonics and overtones. A singing voice produces a rich harmonic series, and a naive FFT detector will often latch onto one of those overtones instead of the fundamental frequency. YIN avoids this by construction.

Each hop returns two values: a frequency in Hz and a confidence score between 0 and 1. Only results in the 80 to 1200 Hz range with confidence above 0.3 are accepted. The best result from the two hops is passed through a 3-frame median smoother, which eliminates single-frame glitches without introducing noticeable lag.

aubio YIN 512 hop size 2048 buf size 80 to 1200 Hz range 3-frame median smoother
3b
analysis/rhythm_analyzer.py

Rhythm and phrase tracking

While pitch detection is running, a parallel process keeps a 2-second rolling buffer of raw audio and uses it to understand the rhythmic structure of what is being sung. Onset detection runs every time approximately one second of new audio has accumulated, using librosa's spectral flux method to find note attacks. Running it on every single frame, as earlier versions of this system did, caused the same onset to be re-detected hundreds of times as the buffer slid forward by just 23 milliseconds per frame. Throttling it to once per second of new audio solves this cleanly.

Beyond individual onsets, the analyzer maintains a phrase state machine with three states: singing, phrase_end, and silence. Any gap of 800 milliseconds or more transitions the state to phrase_end, which signals the harmony engine and synthesizer to wrap up and wait. Tempo is estimated from the distribution of inter-onset intervals and updated every two seconds.

librosa onset detection spectral flux BPM estimation 3-state phrase machine
4
analysis/cree_tokenizer.py

Cree phonetic analysis

When enabled, this stage listens not just to the pitch but to the shape of the sound. It extracts 13 Mel-frequency cepstral coefficients and the spectral centroid from each voiced frame. MFCCs capture the resonant character of the vocal tract, which is what makes one vowel sound different from another even at the same pitch. The centroid captures the overall brightness of the sound. Together, these features are mapped to a PhonemeProfile with three values: brightness (0 is dark, 1 is bright), vowel color (0 is a front vowel like "ee", 1 is a back vowel like "oo"), and nasality (0 is oral, 1 is fully nasal).

The goal is not to identify or reproduce Cree language. It is to mirror the physical feeling of what the singer's mouth is doing, so the robot's voice shifts its timbre in sympathy. If a trained sklearn model is available at the path specified in config, it is used for classification. Otherwise the system falls back to the heuristic feature rules.

13 MFCCs spectral centroid Cree vowel mapping optional sklearn model
5
synthesis/harmony_engine.py

Harmony decision

Given a detected pitch, the harmony engine decides what note the robot should sing. It starts by maintaining a rolling history of the last 32 detected pitches, which it uses to infer the current musical key. Key inference runs once per second using the Krumhansl-Kessler algorithm: the distribution of pitch classes in the history is compared against reference major and minor tonal profiles via Pearson correlation, and the root and mode that produce the best fit are selected as the current key.

With the key established, the engine computes the raw harmony pitch by transposing the singer's note upward by the configured interval (0, 4, 7, or 12 semitones for unison, third, fifth, or octave). It then snaps that pitch to the nearest note in the detected scale, so the robot's response is always musically valid. Finally, the engine compares the new target to the note it is currently holding. If the two are within 5 Hz of each other, it issues a "sustain" action to keep the current note playing. If they differ, it issues a "sing" action to start the new note.

Krumhansl-Kessler profiles scale-lock major / minor detection configurable interval sustain logic
6
synthesis/vocable_synthesizer.py + output/timing_sync.py

Synthesis and playback

When the harmony engine issues a "sing" action, the synthesizer generates the audio. The default engine is additive sinusoidal synthesis with formant shaping. Each of the four vowel shapes (aah, ooo, mmm, hey) is modeled with two formant peaks, F1 and F2, which are the resonant frequencies that define the acoustic character of each vowel. The Cree phoneme profile from stage 4 shifts these formant frequencies dynamically, so the robot's vowel quality follows the singer's in real time. A 30 millisecond crossfade is applied between successive notes to eliminate clicks at note boundaries.

The synthesized audio is handed to TimingSync, which schedules playback 70 milliseconds after the note was detected. That delay is intentional. It gives the robot the feel of a real performer responding with a slight human lag, rather than an instantaneous echo that would feel mechanical. The audio is played back through sounddevice on the configured output device.

additive synthesis F1 / F2 formants 30ms crossfade 70ms response delay sounddevice

Scale Lock
Why the robot never plays a wrong note
After computing the raw harmony pitch, the engine snaps it to the nearest note in the detected key. The key is inferred every second using the Krumhansl-Kessler algorithm: the pitch class distribution of recent notes is compared against reference major and minor profiles using correlation, and the best-matching root is selected. This means that even if the interval calculation would land on an out-of-scale note, the engine nudges it to the nearest valid scale degree. The result sounds intentional rather than accidental.

Cree Phonetic Layer

The robot doesn't just match pitch. It matches feeling.

When the Cree tokenizer is enabled, the system analyzes the phonetic character of each voiced frame and uses it to shape the robot's voice. The goal is not to reproduce the Cree language but to mirror its resonance and vowel quality.

Cree vowel mapping
long-a Bright, open front vowel. High spectral centroid. aah
long-e Very bright, tense. Highest spectral centroid of all vowels. hey
long-i Bright and close. Front of the mouth. hey
long-o Dark, round back vowel. Low spectral centroid. ooo
nasal-n Strong nasal resonance. Mid-range brightness. mmm
nasal-m Full nasal resonance. Dark and rounded. mmm
How the classifier works

The classifier extracts 13 Mel-frequency cepstral coefficients (MFCCs) and the spectral centroid from each voiced frame. MFCCs capture the shape of the vocal tract, which is what distinguishes one vowel from another. The centroid captures the overall brightness of the sound.

In heuristic mode (no trained model), these features are mapped directly to brightness, vowel color, and nasality values using acoustic rules. The PhonemeProfile that comes out the other side is used by the synthesis engine to adjust the robot's F1 and F2 formant frequencies in real time.

@dataclass class PhonemeProfile: vowel_color : float # 0=bright front 1=dark back nasality : float # 0=oral 1=fully nasal brightness : float # 0=dark 1=bright influence : float # how much this shapes timbre
