# Archer-Robot Vocal Collaboration System

A real time system where a robot listens to a singer and harmonizes back live, using synthesized and neurally rendered vocables that echo the phonetic character of Cree singing without speaking the language. Built around a live pitch and rhythm tracking pipeline, a harmony decision engine, a two stage vocal synthesizer (DSP plus optional neural voice conversion), and a companion research web app for Cree language tools, sentiment analysis, and transcription.

## What this actually does

There are two ways to run this project, and they share almost all of the same underlying code.

1. **Live performance mode.** A microphone feeds a real time pipeline: pitch detection, then rhythm and phrase tracking, then a harmony engine that decides what the robot should sing (unison, third, fifth, octave, drone, call and response, and so on), then a vocable synthesizer that renders the actual sound, optionally re-skinned through a trained neural singing voice.
2. **Web app mode.** `server.py` runs a FastAPI server and browser frontend with everything above, plus a set of standalone research tools built on the same audio stack: Cree word and morphology lookup, sentiment analysis, offline speech to text transcription, live streaming captions, and a notes-grounded chat assistant.

### The core pipeline (live performance)

```
mic -> AudioCapture -> Preprocessor -> PitchDetector (yin/rmvpe)
                                     -> RhythmAnalyzer (tempo, phrase state)
                                     -> CreeTokenizer (phoneme profile)
                                             |
                                     HarmonyEngine.decide()
                                             |
                                 VocableSynthesizer.synthesize()
                                             |
                        [optional] Neural Timbre Converter (RVC sidecar)
                                             |
                                     TimingSync -> speaker
```

- **Pitch detection.** `yin` is the default: fast and cheap to run on CPU. `rmvpe`, a real neural pitch model, is also available and pre-warmed at server startup for higher accuracy.
- **Harmony engine.** Decides the musical response (interval, mode, texture, number of voices) based on what the singer is doing, the tempo, and where phrases begin and end. It also includes a configurable sound cue that can trigger a silence response.
- **Vocable synthesizer.** The DSP layer (sinusoidal, wavetable, or formant synthesis) always works with zero extra setup. Its output can then be routed through a neurally trained voice.
- **Neural voice conversion (RVC).** This runs as its own separate process on purpose. `rvc_server.py` is a local sidecar (`http://127.0.0.1:8801` by default) so a heavy PyTorch and RVC stack never blocks the real time audio loop. `server.py` calls it over HTTP per note when `synthesis.neural.enabled` is `true`, and falls back to plain DSP audio automatically if the sidecar is down or a voice fails to load. Check `/neural/status` on the main app and `/health` on the sidecar itself.
  - One honest limitation, straight from the code: the neural stage currently re-skins the whole mixed DSP ensemble through one trained voice, not each choir layer separately. A true multi-timbre neural choir would need the synthesizer to expose per-voice audio stems before mixing. That is a real gap in the current version, not a bug.

The shape now: the singer rests, the drone rests (it breathes with the song); a phrase starts and it makes ONE real onset, its single word for that phrase; everything after that is `sustain`, the same note at the same pitch with no re-articulation; and the note itself is that phrase's own key root placed in the register a fourth to an octave beneath where the singer is, clamped only by whole octaves into a band a sung voice renders warmly (70-262 Hz), because a vocal drone an octave and a half under a line stops sounding like a voice and starts sounding like a foghorn. A small fixed trim and the mode's own reverb keep a note held for a whole phrase from reading as the loudest thing on the panel. Measured on a two-phrase test line: exactly two onsets, one per phrase, each pitched to its own phrase, and the whole part silent through the gaps between them |
| Pitch analysis of an uploaded track | `/api/pitch/analyze-track` | yin/rmvpe |
| Notes grounded chat assistant | see the "Chat" tab in the frontend | Only answers from notes it has explicitly been given |

### Cree speech recognition

This is the one part of the project that exists because of what the language is rather than because of what the robot does, and it is worth being exact about what it is made of.

**Whisper cannot transcribe nêhiyawêwin, and no setting makes it.** `language="cr"` is not a Plains Cree decoder; it is the English decoder with a tag on it, and what it returns for sung Cree is English words -- fed the robot's own vocable takes it answers things like "well, hooray!", because its language model is doing the job it was trained for and snapping unusual syllables onto the nearest common English sequence. That is a property of the weights, not of the search, so beam size, temperature and `best_of` do not move it. So the language is read by its own stack instead, and this is the honest description of it:

* **Acoustic model.** `facebook/mms-1b-all`, which was trained on Cree, with both Plains Cree adapters loaded and used together. One 1B encoder pays for both scripts.
* **The ensemble is real.** A beam search can only score texts its own model produced, so each adapter's hypotheses are handed to *both* adapters, scored with the exact CTC forward algorithm, and averaged. The two adapters make different mistakes -- the syllabics adapter is far more confident and far less accurate on ordinary Roman text -- and averaging two models that fail differently is the oldest reliable result in speech recognition. This is also why `analysis/cree_asr.py` can compare two readings of the same audio at all.
* **The objective is the language.** A lexicon of 15,931 lemmata (the descriptive analyzer's own word list, `tools/fetch_cree_lexicon.py`), a character n-gram model over the project's own Cree corpus plus the Bible, the twelve consonants and eight vowels of Standard Roman Orthography with the `hk` coda, and syllable phonotactics. Every non-Cree symbol is floored to `1e-12`, so English is not unlikely, it is unspellable. This is measured, not asserted: `tools/check_cree_transcription.py baseline` runs the released model's own argmax recipe on the same audio, with nothing masked and no language model, for comparison.
* **Two readings per span, decided honestly.** The lexicon-constrained search competes with a phone-recogniser reading (`facebook/wav2vec2-lv-60-espeak-cv-ft` mapped onto the language's own syllables) that knows no words at all, because a sung syllable is often not a word. Which reading wins is decided by how much the language model likes the letters, and neither winning is the same as being confident: every segment is labelled `cree`, `vocable`, `mixed` or `uncertain`, and an `uncertain` segment is reported as syllables-with-a-question-mark rather than as a word nobody sang.

**What it measures on real speakers.** The only real nêhiyawêwin speech with exact references this project has is the Cree Literacy Network's "Congrats Grads" set: seven recordings, each a fluent speaker, each with the line written down. Character error rate against those references, through the whole stack with separation off (`gold --set isolation=off`; the endpoint's own default pass is Demucs, and it returns the same readings to within a fraction of a percent on every line -- mean CER 57.7% and coverage 3.0% through `/api/cree/transcribe` -- which is the measurement that says Demucs is neutral on a solo voice):

| recording | CER | coverage error | extra | English words |
|---|---|---|---|---|
| `Grad_DSand_pl_line4.m4a` | **0.0%** | 0.0% | 0.0% | 0 |
| `Grad_DSand_sg_line3.m4a` | **0.0%** | 0.0% | 0.0% | 0 |
| `Grad_JOkimasis_line2.wav` | **2.7%** | 2.7% | 0.0% | 0 |
| `Grad_SRatt_line7_8.m4a` | **3.8%** | 3.8% | 0.0% | 0 |
| `Grad_SRatt4_line1.m4a` | **5.9%** | 4.4% | 1.5% | 0 |
| `Grad_WJackson_line5.m4a` | 122.2% | 7.4% | 114.8% | 0 |
| `Grad_SBird_line6.m4a` | 279.5% | 2.6% | 276.9% | 0 |
| **mean** | 59.2% | **3.0%** (median 2.7%) | 56.2% | **0** |

Five of the seven are read out at 0-6% CER, and the mean is what it is because of the last two -- which is a fact about the recordings, not about the transcriber. `Grad_SBird_line6.m4a` is 16.4 seconds long for a seven-word line (2.6 characters per second, a third of this corpus's own speaking rate); it holds several takes of the Cree line, then, from 10.5 s, the English translation that ships beside it -- "you make all your relations proud", which the reading reconstructs from the audio -- and then "congratulations". `Grad_WJackson_line5.m4a` holds the line twice: the sliding-window decode reads the first attempt at 0.7-3.3 s and the second at 3.4-7.6 s, in the model's own two different spellings of the same words, so both attempts are in the audio. Both readings are therefore *correct transcriptions of the take*, and the reference covers only one line of it.

The harness does not hide this and does not correct for it by hand. It reports the error split into what the line was supposed to hold and was missed (**coverage**, which is 3.0% mean and 2.7% median) and what was said beyond it (**extra**), and it gathers the evidence for the surplus rather than asserting it: for each take it checks whether the reading contains the *English translation that ships with that line number*, and prints it when it does. The tuning objective in `sweep` is coverage error for exactly this reason -- scored by CER, a weight set would be rewarded for reading *less* of a take like these, which is the opposite of the thing being asked for. And the number that answers "how well does it hear a speaker" is the one the harness prints beside it: **5 of 7 takes are read out as the line and nothing else, at a mean CER of 2.5% and a worst of 5.9%**, with zero English-shaped words in any of the seven.

**What the released model gets on the same audio**, by the same metric (`baseline` mode, argmax, no language model, nothing masked): mean CER 74.6% on the gold set with a 16.3% coverage error from the Latin adapter alone -- 26.9% at the median, so it does read the easy ones -- and the syllabics adapter alone is not usable on Roman text at all at 95.0% coverage error. So the stack above is worth about 15 points of mean CER and 13 points of coverage error on real speakers, and on the five clean takes it is the difference between "mostly right" and "exact".

**One honest limit, measured and not hidden.** On synthesised speech (MMS-TTS crk, `tts` mode, 36 corpus sentences) the stack reads at 37.1% mean CER against the released model's 39.6%, i.e. almost no improvement -- because *both* are at the acoustic floor there, not because the decoder is doing nothing: the MMS-TTS voice speaks those sentences at 8-11 characters per second where this corpus's real speakers read at 3.3-8, and the ASR, which was trained on real speech, under-produces on it (`Grad_SBird` has the same signature at 2.6 chars/s in the other direction). The clean-speech set is a useful regression check over hundreds of utterances, but it measures the TTS voice's mismatch as much as the transcriber, which is why the real-speaker set above is the number quoted. Every figure in this section is reproducible: `python tools/check_cree_transcription.py gold tts baseline --set isolation=off` for the harness numbers, and `python tools/check_cree_endpoint.py` for the same recordings posted through the endpoint the browser talks to.

**One search setting that measurement reversed.** The beam used to charge a penalty per repeated 6-gram while it searched, written to stop a CTC model that had lost its place from looping. On this gold set it was doing harm rather than good: the two takes that really do hold the line more than once came back with the repeat suppressed and the *first* attempt mangled around it, so it was penalising audio instead of a defect. It now defaults to zero -- coverage error 3.0% against 3.9% -- and repetition is still judged, over a whole finished reading rather than frame by frame mid-search, where `rank_repeat_weight` earns its place (turning that off costs 4.8% against 3.0%). The knob remains for a genuinely noisy take; nothing measured here needed it.

**Running it.** `python download_cree_model.py` fetches the models (~5.5GB, once). `python tools/check_cree_transcription.py health` says whether they load, `gold` and `tts` say how well it reads, `vocables` and `sung` say what it does on the robot's own takes, and `sweep` looks for better decoder weights by coordinate descent. A machine with no live model, no Demucs weights or no network is a normal state: loading is lazy and guarded, `/api/cree/transcribe/health` reports exactly what is missing, and a take with no voice in it returns an empty transcript with notes rather than an error.

**On the live transcription specifically:** it actually runs two ASR models at once, for a good reason. Vosk streams continuously and shows a rough caption almost immediately, in faded italic text. Whisper is much more accurate but only produces a result once it detects a pause in the audio, which barely happens during singing. So Vosk keeps something on screen the whole time, and whenever Whisper catches up, its cleaner result quietly replaces Vosk's rough guess. Neither model transcribes Cree: both are English only and no config setting changes that. **For nêhiyawêwin the panel does not go near either of them.** The Sing live transcript posts each finished phrase to `/api/cree/transcribe` and shows what the Cree stack read, in the script it was sung in and in syllabics, because showing English words for sung Cree is the failure that panel exists to not do.

### The interface

The frontend is still one file, but the look is now its own layer on top of the tool markup: `frontend/assets/site.css` re-tunes the old tokens and draws two stages: the light, full-bleed paper the filmstrip and the tools sit on, and the dark, teal-rimmed stage the About page uses. `frontend/assets/site.js` drives the home filmstrip, the animation that opens a section, the section menu and the scroll reveals. The section menu is a sheet of paper that slides in over a frosted page: the glass is switched on in the same frame the panel is, so the page behind it is already soft before the panel has finished arriving, and the panel's own head, rows and foot walk in behind it one line at a time. Nothing in the tools depends on either file beyond markup hooks, so the pipeline pages keep working if they are removed.

The home page is a filmstrip and nothing else: seven tall plates, one for each entry in the menu, the six instruments of the system and the live demo, dropped on a hand-set vertical stagger. At rest every plate is a pale ghost of itself and the caption under the strip carries the name of the whole thing; the plate under the pointer opens to twice its width in full colour, its neighbours slide outwards to make the room, and the caption writes the section on. The strip only moves when it is hovered, clicked or driven by the arrow keys, and the page is exactly one screen tall, so it never scrolls. Each plate is a door into the site, and opening one plays the reference's own open move, `itemSelected` in their bundle, with every number of it theirs, matched against a recording of it frame by frame. It runs on one timeline. First the row is put on one line: every plate slides down its own stagger step and lands beside its neighbours, and the one you clicked comes out of the row and settles with them. At 0.65s a sheet of black is switched on, already the exact size and place of the plate, scaled down to its slot, so switching it on costs nothing, and over the second that follows the plate is blown up until it covers the window and dissolved into that black over the first half of it, the black growing at the same rate from the same rectangle, and the plates either side of it shoved out of the row in the same breath. Meanwhile the chrome clears the stage: the bar out of the top and the caption out of the bottom, over 1.5s on the same curve. At 1.65s the window is black, so the destination page swaps underneath it and the black is lifted off, which is where this parts company with the reference: they open a film on top of that black, we open a page.

Three things about that move are worth keeping in the code. The plate is lifted out as a copy of its own markup, pinned where it already stands, so the first frame of the flight is the frame you clicked and nothing jumps. It is blown up by one number on both sides, `scaleToFill`, whichever of width and height needs more to cover, so the art is never stretched, only magnified; this is a plate taken from 194 x 437 to 1460 x 3279 on a 1460 x 810 window, so the photograph is softer at the end of the move than at the start, and its file is 644 x 1448. That is the trade the reference makes too, and the fade is over the first half of the blow-up, so the soft end of it is barely on screen. And their curve is a CustomEase written as `M0,0 C0.6,0 0.1,1 1,1`, slow off the mark, quick to arrive, which is exactly `cubic-bezier(0.6, 0, 0.1, 1)`, so the whole move is CSS transitions and a pair of timers rather than a tween library, and the plate and the sheet are each one scale and one translate on the compositor instead of six animating box properties. The black sheet sits under the plate and is the same rectangle at every instant, so the plate dissolving there is a rectangle of colour going dark rather than a cross-fade, which is what their recording shows: a growing black panel with the row still crowded against the window's right edge. Asking for reduced motion skips the whole move and swaps the page directly.

The way back is the opposite move, and it is theirs too, taken off a screencast of the reference's own close frame by frame: nothing slides, nothing is scaled, nothing is blown up. The section washes out where it stands, their whole view, plate and captions and thumbs and the title of the section, reads 52, then 90, then 171, then 222 of their paper between 1.75s and 2.05s of the recording, and then the front door resolves up out of the paper, their row reading 30% of its final contrast at 2.28s and 100% at 2.66s. One second, one curve, and it is the same curve the open move runs on: slow off the mark, all of it at the end, `cubic-bezier(0.6, 0, 0.1, 1)`. So the close is a veil of the page's own paper over the whole window: up over 300ms, held for a 220ms beat while the page is swapped underneath it and the window is put back at the top, then lifted over 460ms. The row is the arrival, not the paper, and that is the half of the move it is easiest to leave out. In their recording the row is *not there* when their paper is reached, their band reads 0.2 to 0.5 of their paper at 2.20s and 2.28s, which is nothing but the noise floor, and then resolves in place over the half second after it, every plate legibly there by 2.90s, and the per-slot readings say in what order: the two outer plates carry signal first (2.33s), the pairs step inward behind them, and the middle plate of the row, the one a hand would reach for, is last (2.70s and 2.78s). So the front door's plates resolve from nothing, edges inward, 45ms apart, on the settle curve (`cubic-bezier(0.22, 1, 0.36, 1)`: most of the way in the first quarter of each plate's own half second, then a quiet), and the caption comes up behind them on one beat, the way it does on a fresh load. Nothing moves but opacity: their plates resolve where they stand, and a row that slides as it arrives is a different move from the one in the recording. The veil also lifts on the settle curve rather than the stage curve, on the stage curve nine tenths of the row's appearance lands in the last 150ms, which is how a fade of paper over an already-arrived row reads as a page turning up rather than as a row arriving. The veil is a sheet rather than an opacity on the leaving page because an opacity would have to fight every transform, filter and compositing layer that page has built, on the artist's page that includes a playing take's own layers, while one element over the top of all of them cannot be defeated by anything underneath it, and since it is the paper the pages are already painted on, the moment it is opaque there is no seam to see: the wash reads as the page dissolving rather than as a sheet coming down. It covers the bar as well, because in the reference the section's own title leaves with the section it belongs to. Every way home goes through it, the corner control, the panel's own links, the panel's back button, the wordmark, the browser's back, because every one of them ends up in `showPage`, and one way home is the point. Measured on the live page: the paper is full at 285ms, the swap happens at 320ms with the window already back at the top from 2600px down, and the plates are all at zero behind the paper. The paper is at 0.14 and the row reads 0.89, 0.78, 0.58, 0.26, 0.58, 0.78, 0.89, outer pair first, middle plate last, exactly the measured order, some 450ms after the swap; the veil is at 0 at about 1.0s; the caption is up behind the plates by 1.2s; and the move takes its classes off when the last plate is standing, with no animation left running and the row at its resting wash. Asking for reduced motion gets the front door directly.

A fresh load of that page arrives the way the reference's does, because the whole arrival is their own, read out of their source and kept number for number: the plate in the middle of the row grows out of a sliver a hundredth of its width and half its height, pulled in toward the centre, and is alone for the first second; then, 1.05s after that first beat, the six around it sweep in from their own slivers, each pair starting a hair after the one inside it. Once the strip is up the caption rises their 300px from under the window while the menu bars come down from above and the line under the wordmark settles the last 12px into its place, 12 and not their 300, because that 300px was a link at the foot of their window and this line is a caption under a wordmark: hiding it down the page left an empty slot on a line of its own. Two other numbers are ours rather than theirs, and both are single numbers in `site.css`. The first plate's beat is 120ms instead of their 450ms, their hold is for a landing to settle, and on a reload here it left the window empty for nearly half a second, which reads as a page that failed to load, and the arrival is skipped altogether for a document that has never been painted (a background tab holds its animations at frame zero, so bringing one forward showed the empty first frame of the arrival). It is written as CSS on a single class the markup ships, so the first paint is already the sliver rather than a flash of the finished strip, script only takes that class off when the arrival is over, and it never replays on the way back from a section. Asking for reduced motion skips it entirely.

The scrolled bar is a sheet of paper with a rule under it on every light page, and that rule is deliberately absent on the black stage: on the artist's page the bar keeps no border and no opaque fill, and a soft scrim behind it fades out well below its own bottom edge, because a hard line under a bar on a black page reads as a lid lying over the work rather than as the top of the window. The artist's own page is the other half of that stage, and its one drawing is traced rather than composed: the curl at the top, the wisp of knot under it and the long S down the spine are measured point by point off a screenshot of the page this design was modelled on, then held in a viewBox that is that trace's own bounding box, so at 8.7vw of the window the pen keeps the reference's proportions and its hairline weight instead of becoming a redrawing of it. **Nothing waiting is ever on screen.** The rules that hide what has not arrived
hang off one class, `html.staged`, and script puts that class on at the end of
its own work, in the same tick it builds the masks and before anything is
painted. So a load in which `site.js` never ran, or threw before it got
anywhere, is a finished page: type set, every rule drawn, nothing waiting on an
animation that will never come. It also means the waits are honest. Before this,
only type was hidden while it waited and everything else, cards, facts grids,
the work rows, the links, stood there finished until it crossed the line and
then blinked out and lifted, which read as a page where the top block animated
and the rest had already happened. Measured after the change: 17 units below the
window waiting, and the count of ink inside a waiting unit that is visible is
zero. The same idea covers the artist's pen: the stroke used to be undrawn at
rest and only this page's arrival could draw it, so a load in which that class
never landed showed the line missing and the sentence alone on the screen. The
pen is now whole at rest and the animation draws it over the top.

Two things that pass a code read and fail on screen, both caught here by
measuring the page rather than the file. A hidden state may never outrank the
state that shows it: `html.staged .stage .ln-i` (waiting, `opacity: 0`) sat one
selector deeper than `[data-staged='lines'].on .ln-i` (arrived), so wherever an
animation was not the thing holding a line up, which is exactly the moment a
block settles and its animation is swapped for a standing state, the waiting
rule won and the type vanished again. Type that arrives and then disappears is
this bug and nothing else. And the arrival line has to be the window's own edge,
not a line up the screen: waiting at 86% of the window height left the bottom of
every screen a band where blocks were in view but not yet arrived, which with
the waiting states hidden is a paragraph-shaped hole in the page. Two assertions
catch both, and both are now run after every change: **no unit in the viewport
has invisible ink**, and **the test for a settled line is its opacity, not its
geometry** (bounding boxes are unaffected by opacity, which is why the first
version of these checks passed while the type was invisible).

**The block is the unit.** Every paragraph, list, grid, card and rule became an arrival unit when script read it, and each one is marked when its *own* top comes up the screen, not when the two-screen-tall chapter around it does. **Call and response is composed now, not approximated.** The mode used to answer a finished phrase with a single pitch nudged toward whatever the key estimate happened to be, one gesture per phrase end. It is now the same set of musical rules in every path it runs in, and the rules are read out of the practice rather than invented here: a phrase is tracked as notes, the cadence it came to rest on is read off its last note (a close on the tonic, a rest on the dominant, a lean on the leading tone, or a stop somewhere else), and the answer is a short line in the register below the call that arrives on the tonic, by step, with the ending that the cadence asked for. `synthesis/call_response.py` is that rule set offline, composing the whole part against the whole track at once and reading the key from every note weighted by how long it was held and from where each phrase came to rest; the same rules run causally in the browser for the live panels, where the key is decided as the music arrives and then held until the evidence really moves, because a few notes of melody fit two keys about equally well and an answer is better served by one settled reading than by one that flips every phrase. The numbers it runs on are documented in `config/config.yaml` under `call_response:`: the pause that ends a phrase, the breath before the answer, how far below the call the answer is anchored, the register it is allowed to use, and the takes the answerer may sing. A render may still carry that accompaniment channel (the endpoint still serves it to any caller that asks with `instruments_enabled=true`), and the page now drops it on arrival: only the voice channel of a render is ever played, and the file that was uploaded is the track. The separation itself still runs for the live chunks, because their model input is cut from it. Measured on the uploaded reference track with a one-channel neural render, the track branch of the audio graph runs within 1.3 per cent of the file's own samples at the TRACK VOLUME position, falls to exactly zero when the file's own source is stopped, and the saved mixdown measures 0.0764 rms against the file's own 0.098 at 78 per cent, so what is heard and what is saved are both the file itself. Two smaller rules came out of the same complaints and are worth naming. A background tab keeps playing: nothing on the demo page is wired to the tab's visibility any more, and the only thing that stops its playback, streamer, microphone or in-flight render is leaving the live demo page itself (the X, the menu, the wordmark, the back button, the browser's own back), which all funnel through the same page change. And the Neural mode pills, Live and Full render, set which mode Neural will use and never move the robot voice: picking one while DSP is selected used to switch the engine as a side effect, so a setting nobody touched changed under the hand. The engine belongs to the engine picker, and a mode chosen under DSP is remembered and applied when Neural is chosen.

## Pre-work: models you need before everything runs end to end

Almost every feature here fails safely if its model is missing. You will see a clear `[WARN]` or `[ERROR]` in the startup log, and the matching `/health` endpoint will report something like `"model_not_loaded"`, but the rest of the app keeps running with just that one feature turned off. Nothing breaks silently. Check the startup log to see what actually loaded.

### 1. Public models, one command each

```bash
python download_whisper_model.py        # faster-whisper small.en (about 150MB) and large-v3-turbo (about 1.6GB)
python download_vosk_model.py            # Vosk en-us streaming model (about 1.8GB)
python download_sentiment_model.py       # cardiffnlp RoBERTa sentiment model (about 500MB)
```

Each script is safe to re-run and only needs internet the first time. After that, every model loads from local files with no further network calls at runtime.

### 2. RVC core assets, only needed for the neural singing voice

```bash
python download_rvc_core_models.py       # hubert_base.pt (about 190MB) and rmvpe.pt (about 181MB)
```

These are the two universal building blocks that any RVC voice conversion needs, published by the RVC project itself. They are not specific to any one trained voice.

### 3. The Cree morphological analyzer, public but versioned, grab it by hand

The Cree word validation feature uses ALTLab's open source Plains Cree finite state analyzer. Download the compiled file from the releases page and place it where the code expects it:

1. Go to `github.com/UAlbertaALTLab/plains-cree-fsts`, then Releases
2. Download `crk-descriptive-analyzer.hfstol`
3. Place it at `data/models/crk-descriptive-analyzer.hfstol`
4. Run `pip install hfst`

### 4. Your trained neural singing voices, bring your own

`config.yaml` points at three RVC voice models, and **the order is the panel**:
index 0 is Model 1, index 1 is Model 2, index 2 is Model 3. `female3` is the
newest trained voice and sits at Model 2; `mi-test`, the previous Model 2, is
now Model 3.

```yaml
model_paths:
  - "assets/female2/female2.pth"          # Model 1
  - "assets/female3/female3.pth"          # Model 2 (newest voice)
  - "assets/synthesis_models/mi-test.pth" # Model 3
index_paths:
  - "assets/female2/female2_added_IVF1701_Flat_nprobe_1_female2_v2.index"
  - ""                                     # female3 was trained without an index
  - "assets/synthesis_models/mi-test_added_IVF1003_Flat_nprobe_1_mi-test_v2.index"
```

Restart `neural_env/rvc_server.py` after changing this list: the sidecar loads
its voices once at startup, so a newly added file is not picked up by a running
sidecar (and the panel will keep showing the old set until it is restarted).

Adding or reordering an entry here is enough: the demo builds one button per
entry from `GET /neural/status`, and the line under the picker names the file
the selected number actually loads (for example `Model 2: female3`), so the
number and the voice cannot drift apart silently. Every trained voice also
goes through the same post-conversion clarity stage (`synthesis.neural.clarity`
in `config.yaml`, `neural_env/voice_clarity.py`), which restores up to 3 dB of
the consonant presence a checkpoint lost and guarantees the result stays below
full scale. A voice that fails to load is shown disabled with the reason in
its tooltip instead of quietly singing a different model.

These are voices trained with the [RVC WebUI project](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI). Training your own voice this way needs a set of clean vocal recordings of the person or voice you are training, plus a GPU (or patience, on CPU) to run the RVC training pipeline itself. That training process is outside the scope of this repo. Once you have a trained voice, each one needs two files to be usable here:

- a `.pth` weights file (the trained voice itself)
- a matching `.index` file (RVC's retrieval index, which improves timbre accuracy; it helps but is not strictly required)

Place them at the paths shown above, or update `config.yaml` to point wherever you keep them. Then start `rvc_server.py` and check `GET /health` on the sidecar. It reports exactly which voices loaded and, for any that failed, why.

**A note before naming or sharing any trained voice publicly:** a voice model trained on someone's singing is a recording of their voice in a very literal sense. Before a `.pth` file like this goes into a public repo or a model card, it is worth being explicit about whose voice it is and what permission exists to use it, the same way you would credit and get consent for a recording. That applies here regardless of what the file happens to be named.

### 5. The Cree to English translation model, project specific

`translation/translate_transformer.py` loads a custom trained model from:

```
data/models/transformer_mt.pt
data/models/spm.model
data/models/spm_config.json
```

This model was trained specifically for this project, not adapted from a public checkpoint, so there is no generic download script for it. Whoever trained it needs to provide these three files directly.

### 6. Everything else downloads itself automatically

- **PANNs** (instrument and percussion detection, used in `/api/transcribe/annotated`) downloads and caches its own weights the first time it runs. It needs internet once, and there is no manual step.
- **The RMVPE pitch model** for the live pipeline's `pitch.rmvpe` setting is the same `rmvpe.pt` file from step 2.

## SingSong: generated instrumental accompaniment

SingSong is a second, separate generative system in this repository. It does not
re-sing the uploaded performance, the way the RVC voice models do. It composes
an instrumental that follows the vocal, using the paper's three-stage cascade:
25 Hz semantic codes → 4 coarse SoundStream streams → 8 fine streams, with a
T5 encoder-decoder for the first two stages and a decoder-only transformer for
the third.

The full implementation, exact hyperparameters, data recipe, and the honest
limits of reproducing Google's private 46,000-hour training run are in
[docs/singsong.md](docs/singsong.md). The end-to-end GPU runbook — base
MUSDB training, full Cree stem separation, Cree fine-tuning, evaluation, resume
behavior, serving the Cree checkpoints from the app, and troubleshooting — is
[GPU_RUNBOOK.md](GPU_RUNBOOK.md). The Cree release checklist is
[docs/cree-model-card.md](docs/cree-model-card.md). The longer reference is
[docs/singsong-training.md](docs/singsong-training.md).
Start with:

```bash
python -m sing_song.cli status      # what is configured, what is missing
```

No SingSong checkpoint is borrowed or downloaded. The SingSong panel in the
Live Demo page (`http://localhost:8000/live-demo#singsong`) stays disabled,
with the exact missing paths listed, until the project has trained its own
codec, semantic k-means, stage 1+2 model, and fine model. The old `/singsong`
URL redirects there.

For a Cree adaptation, `tools/fetch_cree_songs.py` downloads **2.196 hours of
real Cree singing** (27 recordings) whose uploaders explicitly chose a Creative
Commons Attribution licence, and can build a small Demucs-paired smoke set. The
provenance and licence stay in `data/cree_songs/metadata.jsonl`; the audio is
git-ignored. See [docs/cree-singsong.md](docs/cree-singsong.md).

## MySong: chords and a band from a melody

`mysong/` is a separate, CPU-only system for the other half of songwriting:
turn a melody into a chord sequence and a rendered arrangement. It is a
from-scratch implementation of Simon, Morris and Basu's CHI 2008 MySong, with
the paper's fixed one-chord-per-bar HMM replaced by an exact semi-Markov
decoder, a discriminative chord model, a learned 24-way key classifier, and an
optional beat-level BiGRU tagger. It also renders a voice-led piano/bass/drum
arrangement, a mix and a MIDI file, which the paper left to Band-in-a-Box.

The full research notes, training recipe, metrics and limitations are in
[docs/mysong.md](docs/mysong.md). The large-corpus GPU recipe is in
[GPU_MYSONG.md](GPU_MYSONG.md). Quick start:

```bash
python -m mysong.cli status
python -m mysong.cli train          # corpus -> model + tagger (CPU, a few minutes)
python -m mysong.cli analyze take.wav --bpm 96
python -m mysong.cli render take.wav --out renders/take --style jazz
```

In the web app, the MySong controls are in the Live Demo page
(`/live-demo#mysong`): drop a take, pick a band preset and key, and render the
mix or the isolated band.

On the 44-song held-out OpenEWLD test split the shipped model reaches **0.592
frame-weighted root / 0.560 core accuracy** with automatic key detection
(**0.977 exact key**), against 0.25 root for the paper's generative observation
under the same decoder and 0.579 for the fixed one-chord-per-bar baseline with
the same tagger. The jump over the original 0.544 model comes from 4,571 extra
lead sheets after removing melody-signature duplicates of OpenEWLD; title-only
deduplication had leaked 40 of the 44 test tunes and was discarded.
The paper's own evaluation was a listening study, not an accuracy benchmark;
the docs explain why that distinction matters.

Rendering now uses sampled General MIDI instruments through FluidSynth when
it is installed (`--renderer auto`), with the former additive synth kept as a
deterministic fallback (`--renderer synth`).

## Running it

**Web app** (recommended, this covers everything: live pipeline controls, Cree tools, sentiment, transcription, chat):

```bash
python server.py
# or: PORT=8080 python server.py
```

Then open `http://localhost:8000` (or whichever port you set).

The frontend is edited live while the server runs, so nothing the browser holds
stays in front of it: the page and everything under `/static` are served
`no-cache, must-revalidate`. This is not tidiness. Every asset is asked for
under a `?v=` number, and the *page* is what carries those numbers, so a page
the browser cached this morning hands back this morning's numbers and this
morning's script, and a hundred edits to `site.js` change nothing on screen. It
happened here for hours: the server had shipped a fix and the browser was still
running the build from before it. Both responses send a strong ETag, so asking
again is a 304, not a download, and a hard reload is only needed once, to leave
the old copy behind.

**Neural voice sidecar** (only needed if you want the neural singing voice, and it should be started before `server.py`, or you can set `synthesis.neural.enabled: false` in `config.yaml` to skip it entirely):

```bash
cd neural_env
python rvc_server.py
# or: RVC_SIDECAR_PORT=8801 ARCHER_ROBOT_CONFIG=/path/to/config.yaml python rvc_server.py
```

Check `http://127.0.0.1:8801/health` to confirm your voices loaded, then `http://localhost:8000/neural/status` to confirm the main app can reach the sidecar.

**Finding your microphone** for live performance mode: open the web app and check `GET /devices`, or call `POST /pipeline/start` with the `input_device` index you want. You can also set a default in `config/config.yaml` under `audio.input_device`.

## Running tests

```bash
pytest tests/test_pipeline.py -v
pytest tests/test_voice_clarity.py tests/test_neural_voice_config.py -v
```

Tests run without a microphone, using synthetic audio, so you do not need any hardware to check that the pipeline logic itself is working. The second pair needs no trained voice either: it holds the demo's model order (Model 2 is `female3`, Model 3 is `mi-test`) and measures the shared clarity stage on a synthetic voice and a deliberately dulled copy of it.

The listening-level sweep lives in `tools/check_quality_sweep.py` (`--base http://127.0.0.1:8000`), and it is the instrument every quality claim in this README was measured with: it drives every mode x texture over a real mix, an a cappella take and a controlled synthetic phrase, one held note per mode, the neural engines and the live chunk path, and grades what comes back (level, clipping, seams, dropouts, clicks, spectral centre, and pitch where pitch can honestly be judged). **Its fixtures are checked before they are used**, because one of them was wrong for a long time and made correct output look broken: `_tone`'s vibrato was written as `sin(2*pi*f0*t*(1 + m*sin(w*t)))`, whose instantaneous frequency carries a growing `m*w*t` term (+830 cents at 3 s, +1090 at 4.5 s), so the sweep's "single held note, known to the cent" fixture was in fact a rising glide. The probe's own estimator read the 233.08 Hz tone back anywhere between 184 and 1002 Hz inside one window, the project's trackers were called wrong for following it, and every render that sang the input's melody correctly failed a nominal-note assertion. The vibrato is now integrated into the phase (`sin(2*pi*f0*(t - (m/w)*cos(w*t)))`, the only form that is a vibrato), the one-note probe measures its own tone first and fails loudly if it is not the note it claims (it now reads 233.33 Hz, +1.9 cents, 221 of 221 frames voiced), and the nominal assertions it was built around are facts again.

## A note on hardware

If you are running this on a laptop with an integrated GPU (for example, an AMD Phoenix or Radeon iGPU), keep `device: cpu` for both `pitch.rmvpe` and `synthesis.neural` in `config.yaml`. These chips generally are not officially supported by ROCm, and the usual workaround to force GPU use is a known hard hang on at least one commonly used chip. CPU performance is kept reasonable through explicit thread count tuning in `rvc_server.py`.

THAT THREAD COUNT IS THE DIFFERENCE BETWEEN LIVE MODE WORKING AND NOT. It used to be `cpu_count - 2`; measured here on a 16-core machine converting the same 8 s chunk the page streams, torch's own conversion time was 8.84 s (1.11x real time) at 14 threads against 6.74 s (0.84x real time) at 6 and 7.10 s (0.89x) at 8. More threads than the model can use makes it slower, this model being a stack of small conv1d layers whose per-op work cannot pay for the thread pool's coordination, and at 1.11x real time a streamed line can never keep up: the page falls behind the track, skips a phrase to catch up, and the listener hears the robot drop out. The sidecar now takes half the cores, capped at 8, which sits in the flat part of that curve (`RVC_TORCH_THREADS` overrides it), and it prints what it chose at startup.

int8 HuBERT quantization is available (`synthesis.neural.quantize_hubert` in `config.yaml`) and OFF by default, and that is a measurement rather than a taste: on the same chunk, int8 features differ from fp32 by an SNR of 11.3 dB at a correlation of 0.964, i.e. the phonetic content the voice is re-sung from is materially different, so it is only worth turning on if a machine cannot manage real time at all. It was unconditionally on whenever the device was `cpu`; sound quality is the priority here, so it is opt-in.

## Current status and known limitations

This project is under active development, and it is worth being upfront about what is and is not finished yet, the same way the rest of this README tries to be:

- **Cree speech recognition exists now, and its limits are measured.** Both Whisper-based engines (Vosk and faster-whisper) remain English only and are still what the English web tools use, but nêhiyawêwin has its own stack at `/api/cree/transcribe` (see "Cree speech recognition" above): 0-6% CER on five of seven real native-speaker recordings, 3.0% mean coverage error across all seven with zero English words, against 16.3% coverage error for the released model's own reading of the same audio. Two honest limits: the gold set is seven short recordings, not a corpus, and the two takes that are not read out cleanly are takes whose audio holds more than the line written down for them (one holds the line twice, one also holds the English translation and "congratulations"). On synthesised speech the acoustic model is the limit and the decoder adds almost nothing -- 37.1% against 39.6% -- so that set is a regression check, not an accuracy claim.
- **Translation quality has not been formally measured.** The Cree to English model is trained and running, but there is no BLEU score, no held out test evaluation, and no human review process in place yet. Treat its output as a research prototype, not a verified translation.
- **The neural voice choir is one voice at a time.** As noted above, live neural re-skinning currently applies to the whole mixed ensemble rather than each harmony voice individually.
- **Dependency versions are not pinned yet.** `requirements.txt` uses lower bounds rather than exact versions in most places, so a fresh install months from now may pull in different versions than what this was built and tested against. Pinning exact versions, or adding a lockfile, would make this more reproducible.
- **Trained voice provenance should be documented before wider release.** As mentioned in the setup section above, any `.pth` voice file that goes into this repo or its model hub should be paired with a plain statement of whose voice it is and what permission exists to use it.

None of this blocks running the project locally for development or performance. It is here so that anyone picking this repo up later, including future collaborators, knows exactly where the edges are.
